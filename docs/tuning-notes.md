左操作の再調整（2026-10-12）では、ユーザーが左5回を実施した記録
`gesture-use-speed-left-01.jsonl`（785フレーム、約19.8fps、撮影失敗0）で認識0回でした。
左向きのフローは出ていましたが、直交方向の成分も大きく、斜め移動として除外されていました。
判定軸を-10°補正し、`AxisDominance` を2.5→1.5、`MaxCrossTravelRatio` を0.4→0.5へ変更。
単に角度を緩めると縦移動の合成テストが失敗したため、主方向の票が
全移動領域（直交方向のみの移動も含む）の50%以上あることも必要にしました。

最終候補の保存画像再生では、今回の左5回をすべて左と認識し、
照明変更後の意図した右5回も維持しました。右記録末尾の日常動作の誤反応1回は残ります。
過去の `gesture-fast-02/03/08/09/10` と `gesture-slow` の操作イベントも維持しましたが、
`gesture-fast-04` の左1回を取りこぼし、`gesture-fast-05/07` では追加の左反応が出ます。
過去のあらゆる設置条件に改善する設定ではなく、現在の設置向けの調整候補です。
中程度の斜め移動を両軸・両方向で認識し、急な斜め移動・縦移動を除外するテストと、
直交移動が多数の場合の票の除外テストを追加し、既存テストとともにASan/UBSanで通過しました。
この候補をACM0へ書き込み、READY到達、87フレームで撮影失敗0、I2C送信11回成功・失敗0、
`tilt=-10.0 / dominance=1.5 / cross_limit=0.50 / fast_gap_ms=100` を確認しました。
変更後に左5回を再試験（`gesture-use-speed-left-tuned-02.jsonl`、786フレーム、約19.7fps）し、
左4回、右への誤判定0回、撮影失敗0回でした。4回目は信頼できるフローが2フレーム、
累積約5.8画素相当で途切れて、通常判定の8画素に届きませんでした。
実機ログと再生のイベントが一致しています。ただし、この新しい画像列は
傾き補正前（高速判定100ms）の設定でも4/5回となるため、この再試験だけでは
改善のすべてを傾き補正の効果と断定できません。

画角・背景の影響を確認するため、保存画像上で中央の広い矩形・狭い矩形・

最新の左試行は全候補とも4/5回のままで、先の左試行や過去の一部の操作は悪化しました。
中央限定は採用せず、実機の設定は維持しています。この比較は縮小後40×30画像の
